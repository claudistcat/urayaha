# 仕様の論点と、実装でどう決めたか

v0.2 の仕様書には、実装に入ると必ず詰まる矛盾がいくつかありました。
v0.3 / v0.4 で潰した分と、実装側で判断した分をまとめます。

---

## 1. v0.2 で見つかった矛盾(v0.3 で解決済み)

### 1.1 識別子と数値リテラルが字句レベルで区別できなかった

数字は `ン`=0 `プ`=1 `ル`=2 `ャ`=3 の 4 進数で、識別子の推奨命名も同じ文字を
使っていました。§8 が定数名として勧めていた `プルャ` は、4 進数として読むと
123₍₄₎ = 27 です。§20 の `ヤハ プルャ = [プ, ル, ャ, プン]` は「27 という数値
リテラルに代入している」とも読め、解析できませんでした。

**解決(v0.3 §1)**: 数値リテラルに `ン・` プレフィックスを必須にしました。
`ン・プルャ` が 27、プレフィックスの無い `プルャ` は常に識別子です。

### 1.2 型注釈が数値と衝突していた

§35 は Int の型表記を `プル` としていましたが、`プル` は数値の 6 です。
`ヤハ ヤハァ: プル = プ` の `プル` が型か 6 か判定できず、§37 の型変換
`プル("プルャ")` に至っては「6("27")」とも読めました。

**解決(v0.3 §2)**: 型識別子を末尾 `ッ` で分離しました。
`プルッ` Int / `プルァッ` Float / `ワァッ` String / `ヤハ?ッ` Bool /
`ムレッ` List / `ウララッ` Map。v0.4 で `ナンカッ` Any / `ナシッ` Void を追加。

### 1.3 予約語が標準ライブラリのメソッド名に多用されていた

§7 は「予約語と完全一致する識別子は禁止」と定めていましたが、実際には
`ス.モグ.ヤハ`(LET)、`プルャ.ハァ？`(IF)、`ス.ツツウラ.ヤーッ`(BLOCK_BEGIN)、
`ス.ウラ.プルャ`(ELSE)と、予約語がメンバ名に使われていました。§63 の EBNF は
`member = "." identifier` なので、この規則のままでは解析できません。

**解決(v0.3 §3 / v0.4 §77, §100)**: `.` の直後だけ予約語を member_name として
許可します。Lexer は予約語トークンのまま出し、Parser がメンバ名へ読み替えます。

### 1.4 全角「！」と半角「!」で意味が変わっていた

§45 の公開修飾子 `イヤッハー！`(全角)と §48 の改行なし出力 `イヤッハー!`(半角)は
この 1 文字だけが違いました。さらに §42 の例外送出は本文が `ワァーッ！`(全角)、
直後のコード例が `ワァーッ!`(半角)で、仕様の内部で既に食い違っていました。

**解決(v0.3 §4, §5)**: `！`→`!`、`？`→`?` を正規化し、意味の区別に使わないことに
しました。改行なし出力は `イヤッハー…`、公開修飾子は別トークンへ(v0.4 で
`ヤッハーヤーハー` に確定)。

### 1.5 EBNF の欠落

`type` 非終端が定義されておらず、型注釈と Optional が文法化されていませんでした。
パイプ演算子 `|>`、Null 合体 `??`、メソッド宣言、タプル分解も EBNF にも
優先順位表にも載っていませんでした。

**解決(v0.3 §7 / v0.4 §84-§97)**: すべて補完されました。

### 1.6 FizzBuzz の例が壊れていた

§79 の例は `プャ` と `ャャ` を使っていましたが、これは 4 進で 7 と 15 です。
3 と 5 のつもりが 7 と 15 になっており、しかもループ上限 `プルル` = 26 の範囲に
7 と 15 の公倍数が無いため、最初の分岐は一度も実行されませんでした。

**解決(v0.3 §9)**: 3 は `ン・ャ`、5 は `ン・ププ` に修正。
`examples/fizzbuzz.ura` は正しく動きます。

## 2. 実装中に見つけた矛盾と、その判断

### 2.1 EBNF と例が食い違っていた(チェーンブロック)

§63 の EBNF は `if_statement = "ハァ？" expression block { "ウラ" ... }` で、
`block` が `ヤーッ … ハァッ` なので `ウラ` の前に `ハァッ` が必要です。しかし
§24・§25・§41・§79・§80・§81 の例はすべて、`ウラ` / `ダメだった…` が前のブロックを
閉じて次を開き、`ハァッ` は最後に 1 つだけという形でした。

**判断**: 例に合わせて EBNF を直しました。全部の例が一貫してその形であること、
`ハァッ` が減って書きやすいこと、match が元から同じ形(§40)であることが理由です。

### 2.2 「字句解析前に Unicode 正規化」はそのままだと壊れる

v0.3 §4 は「ASCII/全角の `!` `?` は字句解析前に正規化」としていましたが、
素直に前処理として掛けると**文字列リテラルの中身まで書き換わります**。
`イヤッハー("ワァ！")` の `！` が半角になり、プログラムの出力が変わってしまいます。

また NFKC を丸ごと掛けるのも危険です。NFKC は `…`(U+2026)を `...` に展開するため、
NULL の `……` が可変長引数の `...` と衝突します。

**判断**: 正規化は Lexer の中で、コード部分を走査するときだけ適用します。
文字列リテラルの中身は生のまま取ります。対象は `！→!` と `？→?` の 2 文字だけに
限定し、`～ ー … ・ ッ ァ` 等は触りません(v0.4 §8 と一致)。

### 2.3 最長一致だけでは `?` と `!` の扱いが決まらない

正規化後は `ヤハ？ッ`(Bool)が `ヤハ?ッ` になるので `?` を語中文字として扱う必要が
ありますが、そうすると Optional の `プルッ?` が 1 語として読まれて壊れます。

**判断**: バックトラック付き最長一致にしました。

1. 語中文字(`? ! … ～` を含む)を最大長で読む
2. それが既知語ならそのまま採用(`ヤハ?ッ` → Bool、`ハァ?` → IF)
3. 既知語でなければ、`? !` を末尾 1 文字だけ取り込む。ただし直後が
   `? . = !` のときは演算子なので取り込まない
4. 自然な語境界より長い既知語が前方一致するなら、そちらを優先

これで `ヤハ?ッ` は Bool、`プルッ?` は識別子 `プルッ?`(型注釈の位置で Parser が
末尾の `?` を Optional として切り離す)、`ヤハァ??ヤハッ` は `ヤハァ` + `??`、
`フゥン?` はユーザー定義の関数名として読めます。

### 2.4 語と語のあいだの空白

すべてがカタカナなので、`ヤハヤハァ` が `ヤハ ヤハァ` なのか識別子
`ヤハヤハァ` なのか、字句だけでは決まりません。

**判断**: 語トークンどうしのあいだには空白を必須にしました(C 系で `letx` が
`let x` でないのと同じ)。`ウラウラ` は 1 つの識別子、`ウラ ウラ` が else 2 つです。

### 2.5 改行の扱い

§64 は「セミコロン不要」ですが、§81 の例は代入の右辺が次の行に続いています。

**判断**: 改行はただの空白として扱います。ただし `ハァーッ`(return)だけは、
同じ行にある式のみを戻り値とみなします。そうしないと値なし return が次の行の式を
巻き込みます。

### 2.6 `イヤッハー` は文ではなく関数

§48 は print を文のように書いていますが、§59 のパイプ演算子の例
`プルャ |> フゥンッ |> イヤッハー` では `イヤッハー` が**値**として現れます。

**判断**: `イヤッハー` / `イヤッハー…` は組み込み関数にしました。文にすると
パイプに載せられません。

### 2.7 例外と Result の統合

v0.4 のエラーコード表には、`ワァーッ！` で投げた例外と unwrap 失敗に対応する
コードがありませんでした。

**判断(仕様側で確定)**: `ワァーッ！` 自体は診断ではなく通常の制御フローです。
`Err(e).なんとかなれーッ！()` は `throw e` と同じ意味とし、どちらも
`ダメだった…` で捕捉できます。どこでも捕まらずトップレベルまで到達したときだけ
`E3006 UncaughtException` を出します。

### 2.8 メソッド内のフィールド参照

§39 のメソッド例は `イヤッハー(ヤハァ)` とフィールドを裸で書いています。

**判断**: メソッドの中では、ローカルにも引数にも無い名前がレシーバのフィールド名と
一致する場合、`コレ.フィールド` へ読み替えます。明示的なレシーバは `コレ` です。

### 2.9 診断の行番号

§67 の例は `main.usa:ルプ:プャ` と、行番号までうさぎ数字でした。エディタの行番号と
突き合わせられません。

**判断**: 10 進にしました(v0.4 §18 で仕様側も同じ結論)。

### 2.10 整数の除算

仕様に規定がありませんでした。

**判断**: `プルッ` どうしの `/` は 0 方向へ切り捨てます。`%` の符号は被除数に
合わせます(C や Go と同じ)。`ン・プルル / ン・プン` は `ン・プル`(26 / 4 = 6)です。

## 3. 仕様に無いが実装した拡張

| 追加したもの | 理由 |
|---|---|
| `コレ`(self) | メソッドからレシーバ自身を渡せるようにするため |
| `ムレッ<T>` のジェネリック引数 | v0.4 §29 で山括弧に確定 |
| List の `ツナグ` / `ナラベ` / `アル?` | 実用に最低限必要 |
| Map の `カギ`(キー一覧) | 同上 |
| String の `ワケ` / `ツナグ` / `ハァ?` | 同上 |
| Result の `フゥン`(値の取り出し) | 失敗理由を捕捉せず読むため |
| `W1006 NotUrayahaEnough` | Strict Mode でアラビア数字を診断するため |

## 4. 既知の制限

- 型検査は「確実に間違っているものだけを落とす」方針です。推論できない箇所は
  `ナンカッ`(Any)に落として通します。§93 が実用モードを認めているため、
  ここで誤検知を出すと言語として書けなくなります。
- 引数の**個数**は検査しますが、引数ひとつひとつの型は検査していません。
- ループ本体で作ったクロージャは、反復ごとではなくループ変数のセルを共有します
  (JavaScript の `var` と同じ挙動)。
- 複合代入(`+=` 等)を添字やメンバに対して使うと、対象の式が 2 回評価されます。
- 整形器が直すのはインデントと行末空白だけです。
