# ADR-0001: イベントループはホストが所有する

- 状態: 採用
- 日付: 2026-09-12
- 対象: v2.x(GUI)、v3.x(ゲーム)
- 関連: [ADR-0002](0002-urab-format.md)

## 決定

**GUI とゲームのイベントループは Host Runtime が所有し、URAYAHA VM は
コールバックを実行する側に徹する。**

URAYAHA 側にループを持たせる API は作らない。

### やらない形

```
URAYAHA
  ↓
ウ～ラ～ ヤー ヤーッ        // URAYAHA 側の無限ループ
    draw()
    update()
ハァッ
```

### 採る形

```
Host Runtime
  ├─ OS Event Loop
  ├─ Timer
  ├─ Rendering
  └─ Frame Scheduler
          ↓ callback
       URAYAHA VM
          ↓
     update / event
```

GUI もゲームも同じイベント駆動モデルになる。

```
クリック発生 → Host → URAYAHA callback
フレーム要求 → Host → URAYAHA update(dt) → Host rendering
```

## 理由

### 1. 性能が足りない

現在の VM の実測値(2026-09-12、Python 3.10、単純なループ 200,000 回)。

```
4.98 秒 → 約 40,000 反復/秒、約 56 万 VM 命令/秒
60fps なら 1 フレームあたり 669 反復ぶん
```

フレームループを URAYAHA 側で回すと、1 フレームの予算が 600 反復程度しか
残らない。Snake や Pong のようにエンティティが数個なら足りるが、
per-pixel 処理や数百体のエンティティには届かない。

### 2. 性能向上を前提に API を設計しない

VM は今後最適化されうるが、**速くなることを見込んで API を決めない。**
速くなったら儲けもの、という扱いにする。

### 3. 現在のアーキテクチャから自然に伸びる

これは「将来できそう」ではなく、**既にある仕組みの延長** である。
`VM.call_value()` がネイティブ関数から URAYAHA の関数を呼ぶ再入経路として
既に存在し、List の `フゥン`(map)や `ハァ?`(filter)がラムダを呼ぶのに
使われている。GUI のイベントコールバックはこれと同じ経路に乗る。

`VM.run()` の底が 0 固定ではなく「いま積まれているフレーム数」になっているのも
同じ理由で、import がネイティブ関数の中から再入するために必要だった。

### 4. v2.x で間違えると v3.x で作り直しになる

GUI のイベントループ API を先に決めるので、そこで URAYAHA 側にループを
持たせてしまうと、v3.x のゲームでそのまま使えず作り直しになる。

## 影響

- v2.x の GUI API は、Window / Widget / Timer をホスト側のオブジェクトとして
  公開し、URAYAHA 側にはコールバック登録だけを見せる
- v3.x のフレームループも同じ形にする。URAYAHA 側が書くのは `update(dt)` 相当の
  コールバックだけ
- ホスト実装(Python 側のツールキット)の API は URAYAHA に露出させない
- 例外がコールバック境界をまたぐときの挙動は、実装時に検証が要る。
  現在の `_unwind` はフレームを遡ってハンドラを探すが、ネイティブ関数を
  またいだ再入の場合の扱いは未検証

## 検証が必要なこと

- コールバック内で発生した未捕捉例外をホストのイベントループがどう扱うか
- `--trace` が再入をまたぐときの出力
- コールバックの実行時間がフレーム予算を超えたときの振る舞い
