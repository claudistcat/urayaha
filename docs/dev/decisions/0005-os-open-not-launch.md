# ADR-0005: 外部プログラムの起動は「OS に開かせる」契約にする

- 状態: 採用
- 日付: 2026-09-21
- 対象: v0.5(`ウロル.イヤッハー`)、将来の Android / iOS ホスト
- 関連: [ADR-0001](0001-event-loop-ownership.md)、[ADR-0002](0002-urab-format.md)

## 決定

`ウロル.イヤッハー(対象)` は、**開く対象を 1 つだけ受け取る。** コマンド名や
引数配列を受け取る API にはしない。

### やらない形

```
ウロル.イヤッハー(["mpv", "--fullscreen", ヤハァ])   // コマンドを起動する
```

### 採る形

```
ウロル.イヤッハー(ヤハァ)   // これを OS に開かせる、それだけ
```

対象はローカルのファイルパスか `http://` / `https://` の URL。デスクトップ実装は
Windows が `os.startfile`、macOS が `open`、それ以外が `xdg-open` に解決するが、
これは実装の詳細であって契約の一部ではない。どの実装でも起動を待たずに戻る。

## 理由

### Android・iOS にはこの形のサブプロセスが無い

URAYAHA はいずれ Android(Chaquopy 経由)や iOS へ載る可能性がある。

- Android でファイルや URL を別アプリに処理させる標準的な方法は
  `Intent(ACTION_VIEW)` であり、子プロセスの起動ではない。
- iOS は CPython の公式サポート(PEP 730)自体が、`subprocess` の呼び出しで
  例外を送出すると定めている。プロセス起動そのものが原理的にできない。

`ウロル.イヤッハー` に「コマンドを起動する」という意味を持たせると、この
2 つのホストでは実装しようがない API を標準ライブラリに埋め込むことになる。

### ADR-0001 と同じ構図

ADR-0001 は「ホスト実装の API は URAYAHA に露出させない」ことを決めた。
`ウロル.イヤッハー` も同じ適用で、**「これを開いて」という意図だけを
URAYAHA 側に持たせ、実際に何をどう起動するか(コマンド・Intent・openURL)は
ホストの責任にする。**

## 結果として生じること

- デスクトップでは `os.startfile` / `open` / `xdg-open` に落ちる
- スクリプトが任意のファイルを OS に開かせられるようになるが、
  `プスン.イヤッ` によるファイル削除や `プルャウラウラ` による任意 URL への
  通信は既に可能なので、質的に新しい危険が増えるわけではない。ADR-0002 が
  置いている「素性の知れないスクリプトを実行しない」という前提の上に乗る
- 将来 Android / iOS ホストを実装するときは、起動処理の差し替えだけで済む。
  `ウロル.イヤッハー` を呼ぶ側の URAYAHA コードは変更不要

## あわせて記録: 時刻を待つループの所有権

`フゥ～ンフゥン.ウ～ラ～` で作る「時刻まで待って何かする」ループも、同じ構図の
問題を抱える。

アプリのロジックは、`ウ～ラ～` を使った自前の無限ループとして書かず、
**「次のアラームは何時か」「今回は何を再生するか」を返す純粋関数として書く。**
ループそのもの(`フゥ～ンフゥン.ウ～ラ～` で待って `ウロル.イヤッハー` で開く
部分)はデスクトップ専用の「ドライバ」に閉じ込める。

Android は `AlarmManager`、iOS は標準の時計アプリが「時刻まで待つ」役目を
持っており、自前ループはデスクトップ以外では意味を持たない。ADR-0001 の
「イベントループはホストが所有する」と同じ構図であり、この場合は
**「時刻を待つループはホストが所有する」** と言い換えられる。

`examples/alarm.ura` がこの形の最初の実例である。「次のアラームは何時か」
「今回は何を再生するか」をループから独立した関数として書き、デスクトップ用の
待機ループにだけ「ここは捨てる」とコメントで明示している。
