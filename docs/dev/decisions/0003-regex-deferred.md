# ADR-0003: 正規表現は保留する

- 状態: 保留
- 日付: 2026-09-12
- 対象: v0.5 以降、判断を先送りする
- 関連: [ロードマップ](../../roadmap.md)

## 決定

**正規表現は v0.5 の標準ライブラリに入れない。**

まず通常の文字列 API を充実させ、v0.6 の dogfooding で実用アプリを書いたときに
「それでも必要」と判明した段階で改めて検討する。

## 理由

ログ解析には強烈に便利だが、**v1.0 に必須かというと必ずしもそうではない。**

これは開発原則の §12(作る → 困る → 仕様を追加する → また作る)をそのまま
適用した判断である。正規表現は表面積が大きく、いったん入れると

- 方言(POSIX / PCRE / どこまで対応するか)
- うさぎ語での API 名
- パターン文字列の書き方(URAYAHA の文字列リテラルとエスケープの相性)
- 診断(壊れたパターンをどう報告するか)

を全部決めることになる。使うかどうか分からない段階でこれを背負うのは、
v0.2 の仕様書が机上で穴を作ったのと同じ失敗の仕方になる。

一方で「文字列の substring / replace / trim / startsWith / endsWith / find /
大文字小文字変換」は、正規表現の有無にかかわらず確実に要る。こちらを先に入れる。

## 判断の材料

v0.6 で次を書いたときに、通常の文字列 API だけで足りたかを見る。

- ログ解析ツール(いちばん正規表現が欲しくなる)
- JSON 整形ツール
- ファイル一括リネーム(パターンマッチでの絞り込み)

足りなければ、そのとき **どのユースケースで何が書けなかったか** を根拠として
この ADR を更新する。

## 代替案

正規表現なしで済ませる場合、`ワケ`(split)と `ハァ?`(contains)に加えて
`find` / `startsWith` / `endsWith` があれば、行指向のログ解析はかなりの範囲を
カバーできる。まずそこを確かめる。
